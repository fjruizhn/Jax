# JAX governance: test B2 de concurrencia estable

- **Fecha:** 2026-10-10.
- **Qué se hizo:** se sustituyó en `TrabajoWorkerTest.test_B2_archivos_del_mismo_trabajo_se_reparten_entre_hilos` el límite temporal `dt < 0.5s` por una barrera de dos participantes, el registro de los dos IDs de hilo y aserciones sobre resultados exitosos. También se hizo determinista `test_R6b_cancelar_antes_de_que_arranque_el_worker_termina_cancelled`, ocupando ambos hilos OCR hasta que la respuesta de cancelación sea observada, y B5 ahora exige que el event loop procese un callback mientras la ingesta sigue bloqueada en el worker.
- **Por qué:** en PR #395, el job `governance` midió 0.5126s para dos operaciones de 0.3s y falló el umbral de 0.5s; el log también registró una pausa de 0.210s en el event loop. El caso demuestra solapamiento observado, pero el margen temporal de 0.2s convertía latencia del runner en falsos fallos. En una corrida local del mismo gate apareció además una carrera preexistente en R6b: `cancelar_trabajo()` cede el loop al executor de I/O y el worker podía terminar antes de construir la respuesta. El test suponía que ese `await` no daba oportunidad al worker. La revisión GLM read-only identificó la misma fragilidad de tiempo en B5 (`max(retrasos) < 0.15s`), que podía confundir carga del runner con un loop bloqueado.
- **Lección técnica:** afirmar concurrencia con sincronización entre workers, no con un umbral de tiempo que mezcla duración funcional y pausas del scheduler. La barrera tiene timeout y el test conserva `BrokenBarrierError` porque `_procesar_una_ruta` captura excepciones de ingesta y las devuelve como resultado. B5 usa orden observable del callback del loop antes de liberar la ingesta, con un watchdog externo como freno. Para probar una cancelación anterior al arranque, se bloquea el executor objetivo y se observa `CANCELLING` antes de liberar los workers; no se presupone que un `await` no ceda el loop.
- **Alternativa descartada:** aumentar el umbral. Podría aceptar una implementación serial y no probaría el contrato de dos hilos.
- **Decidió:** Codex aplicó el cambio bajo la autorización de trabajo autónomo de Fernando del 2026-10-10; queda sujeto a auditoría Tier 3 del SHA final y CI exacta antes de integrar.
- **Evidencia local inicial:** el test B2 pasó en el executor configurado de dos hilos; con un executor serial de un hilo falló por no alcanzar juntos la barrera. Las tres suites del gate governance pasaron 166 tests en Python 3.14.4; una repetición encontró el fallo R6b descrito arriba (165 pasaron), y R6b aislado pasó cinco veces antes de fijar el scheduling. B5 pasó con el executor normal y falló con un executor inline simulado, al observar el callback después de liberar la ingesta. La prueba R6b con workers bloqueados pasa en Python 3.14.4. GLM revisó B2+R6b en `f381c258` (APROBADO; notó que B2 usa el executor inyectado del fixture, alcance intencional). CI usa Python 3.12; los warnings de deprecación y el warning de `AsyncMock` requieren comparación con la corrida CI final.
